# Text-to-SQL 智能查询工具

用自然语言查询电商数仓：**自然语言提问 → 大模型生成 SQL → 安全与口径校验 → 执行 → 有问题自动重写 → 结果表格**。

本项目基于作者自建的 Olist 电商 MySQL 数仓（ODS/DWD/DIM 三层，9 个原始 CSV → 17 张表、9.9 万订单，其中 7 张 DWD/DIM 表对模型开放）。数仓代码未开源，本仓库只依赖这 7 张表的表结构。

## 为什么做这个项目

1. 真实场景：业务方不会写 SQL，分析师每天被问"上月延迟率多少"这类问题
2. 技术闭环：接口调用 + 提示词设计 + 效果评估与迭代 + 校验器兜底
3. 有量化结果：20 道评估题的实测数据，能说清每一轮改动带来多少提升

## 实测结果（2026-11-04，模型 glm-4-flash 免费版）

| 版本 | 改动 | 执行成功率 | 口径正确率 |
|---|---|---|---|
| v1 | 只有基础规则 | 85% | 50% |
| v2 | +4 条业务规则 | 85% | 70% |
| v3 | +3 个 few-shot（示例字段有误） | 75% | 55% |
| v4 | 修正示例 + 字段硬约束 + 自纠错 | 95% | 75% |
| v5 | +粒度对齐 / 分组输出 / 中位数 / 环比规则 | 90% | 85% |
| v6 | 粒度规则写成带正反例的详细模板 | 85% | —（失败实验） |
| **v7** | **v5 + 中位数模板** | **95%** | **90%** |

三条关键教训：

1. **执行成功 ≠ 算对**：v1 能跑出 85% 的结果，但一半口径是错的（把单价和运费相乘当销售额）
2. **错误的示例比没有示例更糟**：v3 的 few-shot 里写错一个字段名，准确率掉 15 点
3. **规则不是越多越好**：v6 把粒度规则写成带 SQL 对照的教程，反而让模型丢了基础的字段归属判断

每一版的完整结果都留在 `eval_result_*.csv` 里（含生成的 SQL、执行状态与人工口径判定），可以逐题复核，不是只给一张汇总表。

├── semantic_guard.py    # 执行前：口径有没有错（数据库不会报的那类）

├── text2sql.py          # 主流程 CLI

├── evaluate.py          # 批量评估，输出执行成功率与明细 CSV

## 快速开始

```bash
# 1. 安装依赖
pip install -r requirements.txt

# 2. 配置（.env 已在 .gitignore 中，不会提交）
copy .env.example .env
# 填 DB_PASSWORD 与 LLM_API_KEY（智谱 glm-4-flash 免费）

# 3. 体检
python check_env.py

# 4. 网页界面（推荐，可现场演示）
streamlit run app.py

# 5. 单条提问
python text2sql.py "2017 年每个月延迟率是多少"

# 6. 批量评估（20 题）
python evaluate.py --version v7
```

## 网页界面

`app.py` 只做展示，SQL 生成、字段校验、口径检查、自动重写全部调用 `selfcorrect.generate_and_run`，
**网页与命令行共用一套逻辑**，不会出现两边结果不一致。

界面上可以：

- 切换提示词版本（v1 → v7），当场对比同一问题在不同版本下的差异
- 开关语义校验、调整自动重写次数
- 看到生成的完整 SQL、执行耗时、拦截了几次
- 展开"重写过程"，看模型第一次错在哪、被什么规则拦下
- 查询结果自动判断画折线还是柱状

连续重写失败时，界面会明确报错并展示每一版失败的 SQL，**不输出可疑数字**。

## 提示词迭代方法（这是项目的核心价值）

1. **v1（最小提示词）**：只给问题和表结构，跑完 20 题，记录能跑通几题
2. 分析失败案例并归类（字段猜错 / 口径错 / 语法错 / 多表关联错）
3. **v2**：补业务口径（`is_late` 只对已签收订单有效、客户去重必须用 `customer_unique_id`）
4. **v3**：加 few-shot 示例 → **实测反而下降 15 点**
5. 排查发现示例里写了库里不存在的字段（`product_category_name` vs 实际 `category_en`），
   模型逐字照抄。这条弯路本身值得写进 README
6. **v4**：示例字段全部核对、示例换到评估集外（防答案泄漏）、加"字段名逐字取自 schema"硬规则
7. **v5**：补聚合粒度规则（fan-out）、分组列必须输出、中位数、环比
8. **v6**：把规则写得更细 → **又跌回 85%**，连基础题的字段归属都错了
9. **v7**：只保留 v6 里真正有效的那条（中位数模板），其余回退到 v5

## 校验器设计（提示词之外的第二道防线）

提示词管不住的地方，靠程序检查。所有校验都在**执行前**完成：

| 检查 | 抓什么 | 为什么要程序抓 |
|---|---|---|
| 字段归属 | `p.price` 这种列挂错表 | 不用等 MySQL 报错，还能直接告诉模型正确归属 |
| 比率粒度 | 分子 `SUM(CASE...)` + 分母 `COUNT(DISTINCT order_id)` | 数据库不报错，结果虚高数倍 |
| 金额放大 | 明细表 join 订单级汇总表后求和 | 数据库不报错，金额被乘上件数 |
| `is_late` 误用 | 比率查询的 WHERE 里筛 `is_late = 1` | 会算出超过 100% 的比率 |
| 分组缺失 | `GROUP BY` 了列但 `SELECT` 没输出 | 结果只有数字、没有维度 |

命中后交给 `selfcorrect` 定向重写，最多 2 次。**20 题中有 5 题触发重写，其中 3 题修正成功**；另外 2 题（分组意图误解、多表 join 的 fan-out）重写后仍然不对，系统选择报错而不是输出可疑数字。

如果重写两次还不对，系统**宁可报错也不输出**——这是有意的设计，见下节。

## 安全设计

- **只读**：只允许 `SELECT` / `WITH` 开头的语句，其余直接拒绝
- **限行**：未带 `LIMIT` 时自动追加 `LIMIT 200`
- **禁多语句**：检测到分号后仍有内容即拒绝（防注入与误删）
- **超时**：单条查询 30 秒超时，避免大表全扫拖死
- **纠错不越线**：安全拦截触发时**不做**自动修正，直接上报
- **不确定就不答**：口径校验连续失败时抛出异常而非返回可疑结果

## 一句话概括

> 基于大模型 API 与 MySQL 数仓，打通"自然语言 → SQL → 校验 → 执行"链路；用 20 题人工评估集驱动 7 版提示词迭代（执行成功率 85%→95%，口径正确率 50%→90%），并设计四类执行前护栏，拦截数据库不会报错的语义错误。

## 边界说明（面试要能主动讲）

- 不是微调模型，是**提示词工程 + 工程化封装**，不涉及模型训练
- 两个指标要分清：执行成功率（能不能跑）与口径正确率（算得对不对），**不能混着说 95%**
- 准确率是**自建 20 题小样本评估**，不是公开基准（Spider / BIRD）；换领域会明显下降
- 剩下 2 题：一题是模型误解问题意图（问的是**整体**运费占比，它自己加了 GROUP BY 年月），
  一题是多表 join 的 fan-out（三次生成都被粒度校验拦下，最终选择报错而非输出）
- 校验器只能"拦"，不保证能"修"——这是当前方案的已知上限
- 界面是 Streamlit 单页，够演示用，但**没有登录、没有权限隔离、没有并发处理**，
  与"企业级产品"是两回事；同类商业产品（Snowflake Cortex Analyst、Databricks Genie）
  的核心投入在语义层与治理，本项目的 `BUSINESS_NOTES` 只是其雏形
